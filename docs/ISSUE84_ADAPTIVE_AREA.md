The 2 failing rows resolve to 1 distinct target location(s); the selectors overlap, so this is one physical target seen twice, not two independent failures.

The failing target is a trailing-edge sliver (triangle scale 0.0185) on the sheet more than three chords downstream. Two escalation rounds of the near fan (28:8 -> 56:8 -> 96:8) are not enough there, and the per-face budget is spent on the largest weight terms first, so the sliver keeps a 1.9e-3 residual. This is the declared-threshold failure: the adaptive evaluator is faster and is accurate where the estimator is small, but it has no mechanism that subdivides a degenerate near-singular triangle.

Cost basis: both columns time one `limits()` call for the same point through the same API, so the ratio is like for like. The production call integrates every triangle with the fan at 28:8 plus the refined 48:8 sample, while the adaptive call uses the fan only on the near set and composite Duffy elsewhere. The 0.618 s/point quoted in `docs/issue84/velocity_profile_109.json` is the batched area-term kernel over many triangles and is not the same measurement.

Adaptive median 6.847 s/point, production fan 28:8 median 13.151 s/point on the same stratified subset (16 points). Escalations over the whole set: median 0, max 2.0.

## 6. What this does not establish

- The far-field composite Duffy kernel has no error bound; only the estimator and the truth subset constrain it.
- Escalation is per target and per call, so the cost is data dependent; the reported seconds are not a worst case.
- Nothing here changes the default evaluator: `analytic_edges` stays the default and the adaptive mode is opt-in.
- A pass on the gate does not authorize the G2 geometry update (task 4).
